## 一、顶层目录布局

```
PiBot/
├── AGENTS.md            # 贡献者与 AI 编码代理的仓库指南（pnpm sync:agents 生成 CLAUDE.md）
├── CLAUDE.md            # 由 AGENTS.md 自动生成，lint 校验两者一致
├── pnpm-workspace.yaml  # pnpm workspaces 声明
├── tsconfig.base.json   # 共享 TS 基配置
├── tsconfig.json        # 项目引用根
├── biome.json           # Biome lint/format 配置
├── vitest.config.ts / vitest.workspace.ts
│
├── apps/                # 产品形态（可执行单元），见第二节
├── packages/            # 能力库（约 50 个 workspace 包），见第三节
├── sdk/                 # 对外插件 SDK（sdk/plugin-sdk）
├── tools/               # 开发基建（只服务开发期，不进产品），见第六节
├── scripts/             # 仓库级脚本（sync-agent-docs.mjs 等）
├── tests/               # 顶层测试：e2e / integration / fixtures
├── design/              # 设计资源（design/canvas）
├── docs/                # 用户文档（guide/zh、guide/en、privacy）
├── patches/             # pnpm patched 依赖
├── THIRD_PARTY_NOTICES  # 第三方声明
└── e2e/                 # 端到端验收（Makefile 驱动）
```

**设计要点**：`apps/` 与 `packages/` 是两条产出线——apps 是「可分发产品」，packages 是「可复用能力」；`tools/` 与 `tests/` 分离（tools 是开发期工具集，tests 是质量资产）。

---

## 二、apps/：产品形态层

| 目录 | 形态 | 技术 | 说明 |
| --- | --- | --- | --- |
| `apps/desktop` | 桌面应用 | Electron + electron-vite | 主产品，内部四区结构见第四节 |
| `apps/cli` | 命令行 | Node | 终端入口 |
| `apps/mobile` | 移动端 | React Native + Expo + TS | Android |
| `apps/relay` | 中继服务 | Cloudflare Worker（wrangler 部署，docker 兜底） | 跨设备消息中转 |
| `apps/runner` | 无头执行器 | Node（bin/ + installer/） | headless 跑 Bot，可独立安装 |
| `apps/browser-extension` | 浏览器扩展 | - | 浏览器接管 |
| `apps/plugins` | 插件宿主 | - | 插件安装面 |

**设计要点**：每个端都能独立构建分发；relay 用 Serverless（Worker）而 runner 用本地进程，按部署形态选宿主，不强行统一。

## 三、packages/：能力库层（核心）

### 3.1 四类包：contract / 实现 / 横切 / 内核

按 `package.json` 中 `"pibot": { "layer": … }` 声明统计（实测全量）：

| 层 | 数量 | 包 |
| --- | --- | --- |
| **cross（横切契约）** | 19 | 所有 `*-contract` 包 + `policy` + `protocol-base` + `observability` |
| **L1 执行与基础设施** | 6 | computer、execution、link、secrets、storage、workspaces |
| **L2 能力与适配器** | 12 | browser、computer-use、credentials、external-agents、images、import、memory、models、office、plugins、skills、tools |
| **L3 Agent Harness** | 2 | **agent**（pi 内核唯一导入点）、brain |
| **L4 编排与服务** | 5 | acp、brain-app、orchestration、runner、scheduler |
| **L5 产品与界面** | 9 | client-core、i18n、protocol、remote、renderer-kit、routines、sdk、teams、ui |

依赖方向：L5 → L4 → L3 → L2 → L1，只准向下；横切（cross）只依赖契约与 L1。由 `tools/dev/domain-boundaries.ts` 在 `pnpm lint` 中强制。

### 3.2 contract 包与实现包的成对模式

每个业务能力拆两个包：

- `@pibot/<能力>-contract`：**纯 zod 接口 + 共享字符串 + i18n 键**，layer 标 `cross`，依赖只有 `protocol-base` + `zod`。例如 `skills-contract/src/`：
  ```
  skills-contract/src/
  ├── index.ts          # 主出口
  ├── full.ts           # 全量出口（./full 子路径）
  ├── api/              # 接口定义：skills.ts / teach.ts / workflows.ts / skill-links.ts / skill-reference.ts
  └── i18n/             # i18n 键定义：skills.ts / teach.ts / workflows.ts
  ```
- `@pibot/<能力>`：实现包，依赖 contract 包；**能力之间只准依赖对方的 contract**，不能 import 实现。

### 3.3 实现包的内部入口约定（/store /brain /ui /host）

实现包的 `exports` 按运行环境切分入口，以 `@pibot/skills` 为例：

```jsonc
// packages/skills/package.json（layer: L2）
"exports": {
  "./brain": "./src/brain/index.ts",   // Node 侧业务逻辑
  "./store": "./src/store/index.ts",   // 持久化（数据存取）
  "./ui":    "./src/ui/index.ts"       // renderer 侧 React 组件
}
```

```
packages/skills/src/
├── brain/     # 业务服务：capability.ts、service/、teach/、plugin-skills.ts
├── store/     # 存储：skills/、teach/（数据存取，多步写走事务）
└── ui/        # 界面：shell/、skills/、teach/、workflows/（React 组件，独立 tsconfig.ui.json 校验）
```

**入口语义**（跨能力包一致）：

| 入口 | 运行位置 | 职责 | 约束 |
| --- | --- | --- | --- |
| `/store` | brain 进程（Node） | 数据持久化、事务、迁移 | 不 import 业务逻辑 |
| `/brain` | brain 进程（Node） | 业务服务与编排 | **不依赖 Electron**（headless 可跑） |
| `/ui` | renderer 进程 | React 组件、主题 token | 不直接访问 Node 能力 |
| `/host` | Electron main 进程 | 系统能力适配（宿主注入点） | 只有需要原生能力的包才有 |

实测带 `/host` 入口的包只有 4 个：`browser`、`computer-use`、`plugins`、`routines`——即真正需要触碰系统能力的能力包才开这个口。

**类比**：一个能力包像一台「三舱一体的小潜艇」——store 是底舱（只管压舱物/数据），brain 是指挥舱（决策），ui 是瞭望塔（对外显示），host 是只有特定艇才装的机械臂接口舱。四个舱通过 package.json exports 划出硬边界，谁也不许从瞭望塔直接爬进底舱。

## 四、apps/desktop 内部结构：进程四区

```
apps/desktop/src/
├── main/          # Electron 主进程：window/、gui/、updates/、sandbox-doctor、
│                  #   browser-adapter/、computer/、host/、linux/（平台差异收在自己目录）
├── preload/       # 预加载桥：attachments、browser-takeover、computer-guard、office-render
│                  #   （每个危险能力一个独立桥文件，最小暴露面）
├── renderer/      # 渲染进程：app/、features/、colors（主题 token 测试）
├── brain/         # brain 宿主区：brain-host.ts、runtime.ts、business-ports.ts、acp-runtime.ts
│                  #   （把 L3/L4 的 brain 装进进程，Electron 能力经 port 注入）
├── link-bridge/   # 跨设备链路桥（main/preload/brain 三区各有一份）
└── shared/        # 进程间共享
```

**设计要点**：
- `brain/` 目录是「装配车间」——packages 里的 brain 是纯逻辑，desktop 负责把它和 Electron 宿主接起来（`business-ports.ts` 定义端口，main 进程提供实现），落实 AGENTS.md 的「brain 不依赖 Electron」硬约束。
- 平台差异（`linux/`）收在 main 下自己的目录里，三个平台（macOS/Windows/Linux）一个接口多个实现。

## 五、protocol 与 protocol-base：接口的单一定义点

```
packages/protocol-base/src/     # cross 层：按领域切目录的 zod 协议
├── app/ bots/ browser/ chat/ computer/ connectors/ credentials/
├── execution/ groups/ permissions/ providers/ runner/ skills/
├── tools/ workspace/ office/ images/ core/
└── subpaths/

packages/protocol/src/          # L5：聚合层
├── aggregate/                  # 聚合导出（UI↔brain 全量方法与事件）
└── subpaths/
```

规则：UI 与 brain 之间的**每个方法与事件**都在这里用 zod 定义，两端共享类型；进边界必解析（IPC/RPC/文件/env/网络/pi 结果）。

## 六、tools/：开发基建（不进产品）

```
tools/
├── dev/                  # 开发期工具全集（重点）
│   ├── domain-boundaries.ts      # 分层依赖守卫（pnpm lint 强制）
│   ├── prompts-gen.ts            # prompts/<name>.md → 生成模块（lint 校验一致）
│   ├── check-i18n-keys.ts        # i18n 键完整性校验
│   ├── check-slot.ts / check-slot-lease.ts
│   ├── policy-matrix/            # 权限矩阵校验
│   ├── tool-plane-digest.ts / tool-plane-baseline.json   # 工具面基线（防工具集漂移）
│   ├── tsc-build.ts / tsc-cache.ts / tsconfig-references.ts  # 构建编排与缓存
│   ├── capability-check.ts / portable-graph.ts / eval.ts …
│   └── role-catalog/ / mcp-adapter/ / cdp/ / relay/      # 领域子工具
├── e2e/                  # E2E 驱动（flows/、fixtures/、runner.mts）
├── fake-llm/             # 离线假 LLM（测试不碰真网络）
├── pibot-dev/            # 开发者 CLI
├── release/ / stats/ / vendor/
```

**设计要点**：项目把自己的「架构纪律」也做成代码——`domain-boundaries`（分层）、`prompts-gen`（提示词一致性）、`tool-plane-digest`（工具面防漂移）、`check-i18n-keys`（文案完整性），全部挂进 `pnpm lint` / `pnpm check` 自动执行。

## 七、与 pi-code-mode 目录结构的对照

| PiBot 模式 | pi-code-mode 现状 | 差距/可借鉴 |
| --- | --- | --- |
| apps/packages 分离，能力以独立包交付 | 单包 `src/{adapter,engine,manager,mcp,tools,explorer}` + `extensions/commands` | 插件形态下单包合理；但 PiBot 的「入口即边界」（exports 划 /store /brain /ui）值得效仿——本项目 tools/ 与 engine/ 之间已靠惯例分层 |
| `*-contract` 包：zod 接口 + i18n 键独立成包 | `src/engine/types/` 手写 TS 接口 | 无独立契约包；接口变更影响面靠 review 把关 |
| 实现包 exports 三入口（store/brain/ui） | 模块按目录分层，无入口白名单 | 可用 package.json `exports`（或 lint 规则）限制跨目录 import 路径 |
| tools/dev 基建：domain-boundaries 等 lint 强制 | `tests/contract/commands-structure.test.ts` 只守命令装配 | 架构守卫只覆盖命令链，分层/import 方向无守卫（对比文档已列为借鉴项 1） |
| prompts/<name>.md 文件化 + gen 校验 | prompt 内嵌 TS 字符串 | 同上（借鉴项 3） |
| platform 差异收单目录（main/linux/） | 无平台差异面（Node 插件天然跨平台） | 不适用 |
| desktop brain/ 装配区 + business-ports 注入 | `extensions/pi-code-mode.ts` 装配层（单例创建、deps 注入） | 思路一致：装配在边缘、逻辑在内核；本项目规模小所以一层完成 |

**核心启发**：PiBot 的目录结构本质是「**用 package.json exports 和 lint 规则把架构画进文件系统**」——包边界=依赖边界=运行环境边界三位一体。pi-code-mode 若引入同思路，最小做法是：给 `src/` 各目录约定一条 import 方向白名单（如 `tools/ → engine/ → adapter/ → mcp/`），用一条 contract 测试递归检查 import 语句即可，不需要拆包。
