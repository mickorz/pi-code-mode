# Tier 模型池化路由可行性分析（借鉴 pi-model-router + pi-dynamic-workflows）

> 分析日期：2026-11-16　|　需求：workflow 脚本不再写具体 provider/model，按档位（如 fast）自动路由；
> 档位可配多模型各带并发上限（fast: A×16 + B×8），20 个并发请求自动在 A/B 间分配
> 关联：REF-004（pi-model-router）、REF-002（pi-dynamic-workflows model-spec 栈）

## 类比理解

现在的 tier 配置像**指名点姓订餐**：菜单写死"fast 档 = A 店"，20 份订单全挤 A 店排队。目标形态是**外卖平台合单调度**：fast 档是一个"运力池"，A 店产能 16 单、B 店产能 8 单；20 单进来，调度器按各店剩余产能自动分派——A 接满 16 单、B 顺位接 4 单（剩余产能继续服务后续订单），用户只面对"fast 档"一个概念。

## 1. 先说一个必须正视的现状缺口（P0 级前置）

源码走读发现：**当前 tier 功能并未真正切换模型**。

- `workflow-runtime.ts:442-452` 正确地把 `tier` 经 `resolveTier` 解析成 `modelSpec`，并写进 `AgentRunOptions.model`（:582）与 AgentRecord/journal（:603, :618）
- 但 `agent-adapter.ts:57` 透传的 `AgentRequest.model`，在 **`pi-agent-adapter.ts` 的 `execute` 中完全没有消费**——`createAgentSession` 调用（:63-70）不传 `model` 参数，子会话永远跑**会话默认模型**

即：tier 目前只是元数据标注。**池化路由的前提是先让单模型 tier 真正生效**，否则一切调度都是空转。

## 2. 可行性结论：**可行**，分两步走

### Step 1（前置必修）：让 tier 真正切换模型

宿主 `createAgentSession` 原生支持 `model?: Model<any>` 与 `thinkingLevel?: ThinkingLevel`（`pi-coding-agent/dist/core/sdk.d.ts:18-20`）。缺口在两处：

1. **模型串 → `Model` 对象解析**：pi-dynamic-workflows 已有成熟栈可直接借鉴裁剪——`src/model-spec.ts` 的 `resolveModelSpecWithThinking`（解析 `provider/model[:thinking]`、provider 级默认模型回退、ModelRegistry 查询、warning 带回）；registry 获取策略也现成：优先共享宿主 registry，降级磁盘自建 `ModelRuntime.create()`（agent.ts:384-460 注释了完整演进）
2. **adapter 传入**：`PiAgentAdapter.execute` 的 `createAgentSession` 增加 `model`（与可选 `thinkingLevel`）参数

预估：解析栈裁剪 ~150 行 + adapter 接线 ~20 行 + 测试 3 例。**约半天**。

### Step 2：tier 模型池 + 按模型并发上限 + 溢出共用

#### 2.1 配置 v2（向后兼容）

```jsonc
// ~/.pi/workflows/model-tiers.json 或项目 .pi/workflows/model-tiers.json
{
  "tiers": {
    "fast":  "a-provider/a-model",                          // v1 字符串写法继续支持（单模型池）
    "fast":  [                                              // v2 对象数组写法：同键覆盖 v1
      { "model": "a-provider/a-model", "concurrency": 16, "thinking": "medium" },
      { "model": "b-provider/b-model", "concurrency": 8 }
    ],
    "big": "anthropic/claude-opus-4"
  }
}
```

归一化规则：字符串 → `[{ model, concurrency: ∞ }]`；`concurrency` 缺省 → 不限（由全局闸兜底）；空数组/全非法条目 → tier 未配置告警回退。

#### 2.2 引擎新增 `ModelPool`（每模型信号量 + 溢出调度）

```
ModelPool（engine 新模块，复用 engine/runtime/semaphore.ts 的 Limiter 基元）
  条目: [{ model: "a...", limit: 16, limiter: Limiter, inflight: 0 }, ...]
  acquire(preferred?) -> Promise<{ model: string; release(): void }>
    调度策略：优先选 inflight/limit 比值最低（剩余产能最大）的模型；
      全部满载 → FIFO 排队，任一 release 时唤醒队首分配到新释放的模型
    20 并发场景自然成立：a 先吃满 16，第 17 个起溢出到 b（b 上限 8），
      合计吞吐 24；a 释放一个槽位后，后续新请求优先回到 a（保持产能均衡）
```

纯逻辑可测：并发 acquire 竞争、满载溢出、释放唤醒、FIFO 公平性、比例分配（16:8 配比下长跑占用比趋近 2:1）。

#### 2.3 接入点（三处，均为既有缝）

| 位置 | 改动 |
|------|------|
| `model-tiers.ts` | 解析 v2 → `ModelTiers = Record<string, string \| PoolEntry[]>`；`resolveTier` 返回池描述 |
| `workflow-runtime.ts` :444-452 | tier 解析处不再直接得 `modelSpec`，而是拿到池 → dispatch 前先 `await pool.acquire()` 得最终 `model` + `release`；run 结束（成功/失败/超时/取消）**必须** release（finally） |
| `pi-agent-adapter.ts` | （Step 1 已接）`createAgentSession({ model })` |

注意点：
- **全局闸（RunManager gate 16）保留**为跨 run 兜底；池闸是"每模型上限"，两层闸叠加语义清晰（谁紧谁生效）
- **journal 键不受影响**：v0.10 已确认 `resolveTier` 结果不进哈希；池内动态选型同理（`modelSpec` 进 record/journal 展示字段，不进 `deltaKey`）
- **cache 无损失**：workflow 各 agent 本就是独立子会话，池化轮转不产生跨请求 cache 耦合；同模型粘性仅在同会话续跑场景有意义（本引擎无此场景）
- **失败换模型**（pi-model-router 的 fallback 链）：acquire 到的模型执行失败时是否自动换池内另一模型重试一次——建议 **P2 再做**（引擎已有脚本层 `fallback()` 原语，先不重复建设）

| 项 | 预估 |

| Step 1 模型解析栈 + adapter 接线 | 半天 |
| Step 2 ModelPool + 配置 v2 + runtime 接线 | 1 天 |

## 3. 风险与边界

1. **模型解析依赖 ModelRegistry**：优先共享宿主 registry（`ctx.modelRegistry`），extension 侧在 `session_start` 抓取后传给 adapter 工厂；拿不到时磁盘自建（参考项目已趟平此路径，含 pi 版本兼容分层）
2. **多 provider 凭据**：池内模型来自不同 provider 时，`SettingsManager.create` 继承的认证需覆盖全部 provider（auth.json 机制）；测试需真实凭据，单测层用 MockAdapter 验调度逻辑即可
3. **thinking 透传**：池条目的 `thinking` 需与 `createAgentSession.thinkingLevel`（clamped to model capabilities）联动，v1 可先不支持、仅 model
4. **调度公平性**：least-loaded 策略在"批量同 prompt"场景可能倾斜（同 prompt 耗时相近，先完成先释放，天然均衡）；无需复杂权重

## 4. 结论

| 项 | 结论 |
|----|------|
| 按档位自动路由（不写具体模型） | ✅ 可行，且**必须先修 Step 1**（现状 tier 不生效是隐藏 bug） |
| 档位多模型 + 各自并发上限 | ✅ 可行，引擎补 ModelPool，配置 v2 向后兼容 |
| 20 并发溢出共用（A16+B8） | ✅ 语义由池调度自然获得，无需显式配比计算 |
| 总工作量 | 1.5~2 天（Step 1 半天 + Step 2 一天 + 测试） |
