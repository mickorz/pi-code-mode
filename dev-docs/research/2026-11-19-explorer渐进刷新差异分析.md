# Explorer 刷新为何"结果出来才一次性更新"——与 REF-001 渐进刷新的差异分析

> 时间：2026-11-19
> 触发问题：面板在 agent 运行期间几乎不动，完成瞬间才整体更新；REF-001（opencode-dynamic-workflows）看起来是"渐进"的。
> 证据来源：两侧源码 + 现场运行数据 `run-1795066839661-cx5u85`（BigTextAgent 单体运行 36.2s）

## 1. 结论摘要

**REF-001 并没有流式显示结果正文**。它的"渐进"来自三处：

1. 每 1s 轮询运行快照文件（`POLL_INTERVAL_MS = 1000`）
2. 快照带心跳（`RUN_SNAPSHOT_HEARTBEAT_MS = 3000`），running 节点状态随之刷新
3. 树行用 `startedAt` 实时算已耗时（`formatElapsed` / `phaseElapsedMs`）

它的**结果正文同样是完成时才出现**：`record.outputPreview` 在 `await run(...)` 之后才赋值
（`thirdparties/opencode-dynamic-workflows/src/runtime/workflow-runtime.ts:593`），
详情面板读 journal（只在成功完成时写入）。

我们的实现**在结构上更实时**（事件驱动，无轮询），但有一个致命缺口：
**agent 运行期间根本不产生任何事件**，因此长任务期间面板完全静止，完成时"跳变"。

## 2. 两侧证据

### 2.1 我们的链路（三段都在"终态才动"）

| 环节 | 代码 | 行为 |
| --- | --- | --- |
| 子会话事件订阅 | `src/adapter/pi-agent-adapter.ts`：`session.subscribe((e) => { if (e.type === "message_end" ...) })` | **只订阅 `message_end`（整条消息结束）**，`message_update`（增量）完全没接 → 运行期无任何文本 |
| Runtime 事件出口 | `src/engine/runtime/workflow-runtime.ts`：`shared.onAgentUpdate?.(record)` | 只在 `started / 终态 / 重试中间态` 调用；没有"运行中阶段性更新"通道 |
| 详情数据源 | `src/explorer/repository/detail-repository.ts` → `JournalStore.getEntry` | journal 由 `onAgentJournal` 在**成功完成时**写入 → 详情必然"完成才有内容" |
| 渲染节流 | `src/manager/render-scheduler.ts` | `agent.updated` 走 500ms 节流、其余即时；但运行期没有 `agent.updated` 事件可节流 |
| 耗时显示 | `extensions/explorer/render.ts`：`fmtDuration(node.durationMs)` | 只显示**终态** `durationMs`；running 节点没有已耗时显示 |

### 2.2 REF-001 的链路（轮询 + 实时耗时）

| 环节 | 代码 | 行为 |
| --- | --- | --- |
| 快照写入 | `src/tools/workflow.ts:174` `tryWriteRunSnapshot(...)`（onAgentUpdate 驱动） | 节点变化即写 `<dir>/.opencode-workflows/runs/<runId>.json` |
| 心跳 | `src/tools/run-snapshot.ts:27` `RUN_SNAPSHOT_HEARTBEAT_MS = 3000` | running 态每 3s 刷新快照，TUI 据此判活 |
| TUI 刷新 | `src/tui/plugin.tsx:171` `POLL_INTERVAL_MS = 1000` | **每秒轮询**快照 → 树/计数渐进更新 |
| 实时耗时 | `src/tui/workflow-store.ts` `formatElapsed` / `phaseElapsedMs` | 用 `startedAt` 现算，running 节点显示秒表 |
| 结果正文 | 同上 `workflow-runtime.ts:593` + `tui/result-view.ts` | **完成时才写 outputPreview / journal**（与本文结论一致：无流式正文） |

### 2.3 现场数据佐证

`run-1795066839661-cx5u85`：

```
SchemaAgent    4.3s    完成后一次性出现
BigTextAgent  36.2s    这 36 秒内面板没有任何变化（无事件、无计时、无正文）
tool           0.02s   完成即出现
```

REF-001 在同样的 36s 里会有：秒表每秒 +1、节点状态每 3s 心跳刷新、计数不变但界面"活着"。

补充证据：节点快照**已有 `startedAt`**（`BigTextAgent: startedAt=1795066844013, durationMs=36203`），
也就是说实现秒表所需的数据已经在树节点上（`WorkflowTreeNode.startedAt`），
缺的只是渲染层"用 startedAt 现算 + 周期重绘"这一步——方案 A 成本因此很低。

## 3. 差异矩阵

| 能力 | REF-001 | 我们（当前） | 差异性质 |
| --- | --- | --- | --- |
| 节点出现/状态变化 | 1s 轮询快照 | **事件驱动（更快）** | 我们更优 |
| running 节点已耗时 | ✅ 秒表（现算） | ❌ 只显示终态时长 | **我们的缺口** |
| 计时/心跳带来的"活着"感 | ✅ 1s 轮询 | ❌ 无周期刷新 | **我们的缺口** |
| agent 运行期部分文本 | ❌ 无 | ❌ 无 | 两侧一致（**都不是流式**） |
| 结果正文 | 完成时（journal） | 完成时（journal） | 两侧一致 |
| 计数/进度 | 1s 轮询 | 事件驱动 | 我们更优 |

**所以真实差距只有两条**：running 节点没有秒表、运行期没有任何周期刷新。
"结果正文流式滚动"这件事 REF-001 本身也没有，是我们记忆偏差。

## 4. 可实施方案

### 方案 A：实时耗时 + 运行期轻量 tick（推荐先做）

- 渲染层：`node.status === "running" && node.startedAt` → 显示 `fmtElapsed(Date.now() - startedAt)`
- 打开面板期间，若存在 running 节点，每 1s 调一次 `requestRender`；无 running 节点则停掉定时器（idle 零开销）
- 成本：约 40 行 + 2 条测试；不碰 runtime / 事件协议 / journal
- 效果：与 REF-001 的"秒表 + 界面活着"完全等价

### 方案 B：运行期部分输出（真正的流式文本）

- `PiAgentAdapter` 增加订阅 `message_update`（pi 已提供 `assistantMessageEvent: { type: "text_delta", delta }`）
- 聚合到有界缓冲（建议 8KB 环形，防长输出吃内存），**500ms 节流**发 `agent.updated`（复用现有 progress 节流通道）
- `AgentRecord` 新增 `partialOutput?: string`（可选字段，**绝不进 journal / 不进 hash**，回放语义不变）
- 详情面板在 `running` 态显示 `-- live output --`（尾部 N 行），完成后被 journal 结果覆盖
- 成本：中等（adapter + runtime 透传 + tree metadata + render + 测试），约 150 行
- 风险：事件量上升（500ms 一次可接受）；必须保证脱敏在渲染侧做（复用现有 `redactValue`）；不得写盘

### 方案 C：照搬 REF 的 1s 轮询快照

**不推荐**。我们已经是事件驱动，再加轮询等于把两条通道并存：
快照文件写盘 + 轮询读盘会给热路径增加 IO，而收益已被方案 A 覆盖。

## 5. 建议路径

1. 先做 **A**（低成本、直接消除"卡住"的观感）
2. 若仍觉得信息不足，再做 **B**（partial output），按 500ms 节流 + 8KB 上限
3. C 不做

## 6. 实施结果（方案 B 已落地，2026-11-19）

| 适配器 | `src/adapter/pi-agent-adapter.ts` | 订阅 `message_update` 的 `text_delta`（thinking/toolcall 分片忽略），`finally` 里 flush+dispose |

### 6.2 真实模型实测

`dev-examples/partial-probe/probe.mts`（单 agent，38294ms）：

```
partial 次数: 11   采样: 33123ms/36字 → 33654ms/69字 → 34168ms/102字 → ... → 38294ms/349字
间隔 ≈ 500ms，尾部长度单调递增；最终结果长度 349 = 末次 partial 长度
```

结论：节流与尾部聚合按设计工作。注意首个 partial 出现在 33.1s——这是模型思考/工具阶段的客观耗时，
文本增量一开始产生就立刻上抛（我们无法提前，也不应该伪造）。

### 6.3 评审发现并修复（第二轮，2026-11-19）

| # | 问题 | 复现 | 修复 |
| --- | --- | --- | --- |
| 1 | 重试时详情先显示上一次 attempt 的旧流式文本 | attempt1 推送 partial 后失败 → attempt2 首次推送带 `attempt-1` 文本（已实测复现） | 每次 attempt 开始 `record.partialOutput = undefined` |
| 2 | schema 修复轮把多轮 JSON 拼在一起 | `partialBuffer` 跨 `prompt()` 累积，tail = `{"round":1}{"round":2}`（已实测复现） | 新增 `PartialBuffer.reset()`，每轮修复前清空 |
| 3 | 异常路径不退订 session 监听 | `catch` 分支直返，`unsub()` 只在成功路径调用 | 句柄提到 try 外，`finally` 无条件 `unsubSession?.()` |
| 4 | 终态后 8KB partial 常驻内存 | 节点终态后 `partialOutput` 不清空 | 成功路径写 journal 前清空（详情改由结果区呈现） |

### 6.4 已知限制

1. **文本增量开始前无输出**：模型长时间思考/调工具期间，详情仍是「（运行中，暂无结果）」，只有秒表在走。
2. **partial 不做脱敏**：它是模型原始文本流（非结构化），键值脱敏不适用；结构化结果完成后仍走 `redactValue`。
3. **成功路径才写 journal**：失败/中止节点完成后详情仍只有 `attempts` + error（与 REF-001 一致）。
4. **tick 的实际行为**：run 节点自身 running 不计入 `hasRunning()`，但 **workflow/phase 节点在 run 期间一直是 running**，
   所以 run 执行期间实际是每秒重绘一次（不是完全静止）；run 结束（workflow 节点转终态）后立即停摆。
5. **partial 无脱敏**：流式文本是模型原始输出，键值脱敏（`redactValue`）只作用于结构化结果；
   若模型在正文里直接吐出密钥，实时区与最终的 text 结果都会显示。需要更强保障时应加正则擦除。

## 7. 验收方法（实施后）

| 项 | 方法 |
| --- | --- |
| 秒表 | 跑一个 ≥30s 的 agent，看 running 节点耗时每秒递增 |
| idle 零开销 | 面板内无 running 节点时，`requestRender` 不再被定时器调用（测试断言） |
| 部分输出（B） | 运行中详情出现 `-- live output --` 且文本增长；完成后被 journal 结果替换 |

| 流式不影响回放 | resume 同一 runId，回放结果与首次一致（journal 未被 partial 污染） |
