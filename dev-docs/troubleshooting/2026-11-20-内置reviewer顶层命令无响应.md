# 内置 reviewer 顶层命令无响应排查

- 日期：2026-11-20
- 症状：用户输入 `/reviewer xxxx` 后没有任何消息、没有启动提示，也没有 workflow 运行记录。
- 影响范围：所有内置 workflow 的顶层斜杠命令（`/coder`、`/reviewer`、`/judge`、`/fixer`、`/quality-loop`）；`/workflows run reviewer ...` 不受此具体前置检查影响。
- 根因修复提交：待本次提交生成
- 复验 reviewer run：`run-1795404514517-1q3bdf`（big，421.1s，`status=completed`）

## 现象复现与证据

内置 workflow 已在 `session_start` 中注册为顶层命令，且 `reviewer` 在 `loadRegistry()` 的合并结果中存在。但顶层 handler 的调用时校验仍使用旧逻辑：

```ts
exists = loadManifest(cwd) != null && loadRegistry(cwd).has(id)
```

内置 workflow 不写入项目 `.pi/workflows/register.json`，所以 `loadManifest(cwd) != null` 为 false。handler 在解析参数、构造 workflow 工具之前直接返回“已注销”分支；该提示在用户场景中未被观察到，于是表现为完全无响应。

真实宿主运行 journal `run-1795403423733-0qua06` 证明：修复后 `/reviewer` 已进入真实 agent 执行，完成一轮针对内置注册与顶层命令的评审（446.1s，结构化 `status=completed`）。

## 根因

内置 registry 于 `0d39112` 引入：`loadRegistry()` 合并“项目来源 + 内置来源”，但顶层命令 handler 保留了“必须存在 manifest”的旧假设。注册阶段已经允许内置无 manifest 注册，执行阶段却再次要求 manifest，形成前后语义不一致。

类似于酒店前台已经为住客发了房卡（顶层命令已注册），电梯门禁却只查预订系统（manifest），不查实际住客名单（合并 registry），于是持卡住客仍无法上楼。

## 修复

将 handler 的存在性检查改成只看合并后的 registry：

```ts
exists = loadRegistry(cwd).has(id)
```

这样：

- 内置 workflow：始终在合并 registry 中，能执行；
- 项目 manifest workflow：注销后从 registry 消失，残留顶层命令仍会被安全拒绝；
- registry 解析失败：仍向用户显示真实错误。

## 同轮评审发现并修复的相关问题

真实 reviewer 还发现 3 个低优先级一致性问题，本轮一并收敛：

1. legacy `.opencode-workflows/workflows/` 可用内置 id 静默遮蔽内置，导致顶层命令丢失或错跑项目脚本；现在 manifest 与 legacy 均拒绝内置保留 id。
2. `extensions/pi-code-mode.ts` 的装配注释仍称“仅 manifest 模式注册”，已改为“内置总是注册，项目仅 manifest 注册”。
3. 自然语言参数的注释称“不足 3 字符”但实现阈值是 2；已统一为“不足 2 字符”。
4. `/workflows` 帮助的 `run` usage 漏掉自然语言指令形态；已更新为 `[<指令文本> | k=v...]`。

## 回归保护

- 新增 contract：内置 `/reviewer` 在无 manifest 的临时项目中仍注册顶层命令，并能通过存在性校验进入执行链。
- 内置 registry contract 增加 manifest 同名与 legacy 同名的拒绝测试。
- 自然语言参数补充两字任务 `修复` 的边界断言，锁定当前“长度至少 2”的行为。
- 全量验证：`npm run build`、engine 220/220、contract 244/244。

## 独立复验

修复后，使用真实顶层命令执行：

```text
/reviewer 审查这次修复是否解决了内置 workflow 顶层命令无响应问题
```

真实运行完成（big 档，421.1s），结论为 `status=completed`：确认内置 workflow 在无 manifest 项目中能注册顶层命令，并通过合并 registry 的存在性校验进入执行链；build、engine、contract 测试均通过。

复验同时提出一条 **medium 遗留项**：当前对“项目来源使用内置保留 id”采取 fail-fast，导致 registry 读取整体失败，可能扩大到同项目其他 workflow 的 run/register/resume 入口。该策略本次保留，因为它能阻止内置命令静默丢失或错跑，且正常 `/workflows register` 已在写入前拒绝该 id；后续若要优化体验，改成“跳过冲突条目 + warning”或为各入口补统一的友好错误转换。此项未在本次未经确认地改变 fail-fast 语义。

## 预防规则

只要有“项目来源 + 内置来源”的合并 registry，所有入口都必须查同一份合并结果，不能在其中一层额外假设某个来源一定存在。以后增加 schedule、completion、direct command 等入口时，优先复用 `loadRegistry()`，不要私自加 `loadManifest()` 作为存在性前置条件。
