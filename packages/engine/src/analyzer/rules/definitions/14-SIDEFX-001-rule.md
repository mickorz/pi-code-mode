# SIDEFX-001：并行候选共享文件/状态副作用

| 元信息 | 值 |
| --- | --- |
| 规则 ID | SIDEFX-001 |
| 严重度 | high |
| 置信度 | 0.80（AI 判定） |
| 检查方式 | **AI 规则检查**（需要判断两个 agent 调用是否写同一路径、是否依赖前一调用的落盘结果） |
| 规则集版本 | 1.0 |

## 检查什么

SERIAL-002 报出的并行候选实际通过文件路径或共享状态存在隐式依赖 → 不能并行化

## 为什么是问题

`SERIAL-002` 只能看到"变量之间没有引用"，但 workflow 里的调用大量通过**磁盘**传递数据：

```js
const rsPatch = await agent('更新分支状态，写入 ' + runDir + '/runtime/branch-status.json')
const rsCards = await agent('读取 branch-status.json 生成卡片配置')
```

两条调用的变量完全没有交集，静态判为并行候选。但第二条读的正是第一条刚写的文件——**并行化会让它读到旧数据或空文件**。

这类误改的后果特别严重：

- 不报错，静默产出错误结果
- 产物看起来结构完整，只是值不对
- 排查成本极高（"为什么卡片配置里状态是 pending？"）

同样的问题也存在于：

- 两个调用写同一个临时文件名（互相覆盖）
- 两个调用读写同一 `runDir` 子路径下的不同文件但目录创建存在竞争
- 依赖前一调用执行的 git / shell 命令的副作用

## 命中判定（实现口径）

对每一组 `SERIAL-002` 候选（源码相邻 + 无变量引用），检查是否满足任一：

1. **路径重合**：A 的 prompt 中出现某个文件路径（或其拼接片段），B 的 prompt 中出现同一路径
2. **写后读**：A 的 prompt 含写盘指令（`write` / `逐字写入` / `保存到` / `写入文件`）指向路径 P，B 的 prompt 含读取指令（`read` / `读取` / `回读`）指向同一 P 或其父目录
3. **同名临时文件**：两个 prompt 都包含同一个临时文件名或同一个输出目录的写入
4. **共享可变状态文件**：两个 prompt 都引用同一个 `runDir`/`state`/`manifest` 路径，且至少一方是写
5. **外部副作用依赖**：A 的 prompt 要求执行 `git` / `node <script>` / 其他命令并产出文件，B 的 prompt 读取该产出

证据必须给出**两处**：两个调用各自的写/读位置与路径片段。

## 反例（不命中）

```js
// 各自写不相关的路径 → 不命中
await agent('把结果写入 ' + runDir + '/a/out.json')
await agent('把结果写入 ' + runDir + '/b/out.json')

// 都只读不写 → 不命中
await agent('读取 a.json 并总结')
await agent('读取 b.json 并总结')
```

## 报出的证据

- 候选组（来自 SERIAL-002 的调用编号与行号）
- 冲突类型（路径重合 / 写后读 / 同名临时文件 / 共享状态 / 外部副作用）
- 两侧各自的路径片段与 prompt 关键词

## 建议怎么改

1. **默认不要并行化**这类候选，即使 SERIAL-002 报了
2. 确需并行时，让两次调用输出到**各自独立目录**，并用确定性脚本（而不是 agent）做合并
3. 若顺序确实必要，在代码里加注释说明"B 依赖 A 的落盘"，避免下次被误改
4. 需要 `git`/`node` 前置副作用的，用 `commandSuccess()` 这类确定性调用显式串行，不要藏在 agent prompt 里

## 已知误报与局限

- 只识别 prompt 里**字面出现**的路径；`p(dir, name)` 这类函数拼接可能匹配不到
- 无法判断运行时的实际写入顺序（并发下谁先谁后）
- 目录级依赖（B 读 A 写的不同文件名，但 A 还负责建目录）可能漏判
- 对 agent 内部自行决定写入路径的场景（prompt 只说"写到合适位置"）无法判定 → 应给 `uncertain`

## 验收口径

1. 对每个被判定为"可并行"的候选组，给出**写入路径清单**并证明两两不重合
2. 并行版本与串行版本对同一输入产出的产物**逐字节一致**
3. 若无法证明独立，则保持串行并在代码中注释依赖原因
