# RETRY-001：重试成本放大

| 元信息 | 值 |
| --- | --- |
| 规则 ID | RETRY-001 |
| 严重度 | low |
| 置信度 | 0.80 |
| 检查方式 | AST 静态分析（`retries: N` 常量） |
| 规则集版本 | 1.0 |

## 检查什么

retries 放大失败场景下的调用量与 token 消耗

## 为什么是问题

`retries: 2` 意味着最坏情况每个调用跑 3 次。若上游输入本身有问题（prompt 错误、上下文超长），
**重试不会成功，只是把同样的失败与 token 消耗重复 3 倍**。

真实案例：48 个并行任务、`retries: 2`、单次 20 分钟 → 最坏 144 次调用 / 约 48 小时墙钟。

## 命中判定（实现口径）

1. 源码中存在 `retries: <number>`；
2. 取最大值 `max`，`max >= 2` 才报（`retries: 1` 是常态，不报）。

```js
// ✓ 命中（max=2 → 最坏 3 倍）
await agent('查证', { retries: 2 })

// ✗ 不命中（max=1）
await agent('查证', { retries: 1 })
```

## 报出的证据

- `retries 最高 N 次`
- `agent 调用点 M 个`
- `失败场景最坏调用量 ≈ M × (N+1)`

## 建议怎么改

1. `retries` 只用于**瞬时故障**（网络抖动、限流）；输入类错误不该重试
2 . 配合 M3 任务级恢复：只重跑失败任务，而不是整 run / 整波重跑
3. 长耗任务（>10 分钟）建议 `retries: 1` 或 0，让失败快速暴露

## 已知误报与局限

- 不区分重试是否配置了退避（`backoff`），也不判断失败是否可重试
- 最坏调用量是**上界估算**（假设全部失败且全部重试满）
- `retries` 从变量/配置读入时不识别

## 验收口径

- 长耗任务 `retries ≤ 1`，或明确只包瞬时故障
- 人为制造一次失败：观察重试次数与总耗时符合预期（不出现整波重跑）
