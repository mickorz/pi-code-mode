# DET-001：确定性任务交给了 LLM

| 元信息 | 值 |
| --- | --- |
| 规则 ID | DET-001 |
| 严重度 | low |
| 置信度 | 0.50（提示性，刚好在计分阈值边界） |
| 检查方式 | AST 静态分析（prompt 前缀关键词） |
| 规则集版本 | 1.0 |

## 检查什么

prompt 语义看起来可用确定性 JS 完成（统计/校验），交给 LLM 是浪费

## 为什么是问题

让模型"数一下有几个"、"检查字段是否齐全"：

- 慢（秒级 vs 毫秒级）
- 贵（token 成本）
- **不可靠**（模型会数错、漏字段）

同样的活 `JSON.parse` + `length` + schema 校验是确定性的。

## 命中判定（实现口径）

`agent()` 的第一个参数是字符串/模板字面量，且开头含以下关键词之一：

| 关键词组 | 建议 |
| --- | --- |
| 统计 / 计数 / 去重 / 排序 / 编号 / 汇总数量 | 用 JS 确定性完成 |
| 校验 / 核对格式 / 字段是否齐全 | 用 JS + schema 校验 |

每组最多报一条（取首个命中的 agent）。

```js
// ✓ 命中
await agent('统计 requirements 目录下的文件数量')

// ✗ 不命中（语义判断/总结，不是确定性计算）
await agent('分析这些需求之间的冲突')
```

## 报出的证据

- `prompt 语义疑似确定性任务：<prompt 前 60 字>`

## 建议怎么改

```js
// 代替 agent('统计文件数量')
const count = fs.readdirSync('requirements').filter((f) => f.endsWith('.md')).length
```

需要模型参与的任务保留（如"判断两条需求是否冲突"），把确定性部分剥离出来。

## 已知误报与局限

- **纯关键词匹配，极易误报**：`"统计"` 出现在字符串任何前部都可能命中（含"统计规则含义"这类语义任务）
- 只看 `agent(` 后紧跟的字面量，拼接/变量 prompt 不识别
- confidence 0.50 是刻意压低的：作为"值得看一眼"的提示，不该主导风险分

## 验收口径

改完后该调用消失，或改为混合模式（JS 做统计，模型只做语义判断）；
统计结果与手工核对一致（确定性可复现）。
